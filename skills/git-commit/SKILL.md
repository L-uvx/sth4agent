# Git 使用规范

## 一、禁止自动提交

- **禁止**执行 `git commit` / `git push` / `git add`（入库相关操作一律不代做）
- 即使用户说「提交」「commit」「帮我提交」，也**只生成入库信息**，由用户自行入库到本地仓库
- 不擅自改 git config、跳过 hooks，或做破坏性操作（除非用户明确要求）

## 二、改动后的检查顺序

本地修改代码后，按以下顺序处理，**全部通过后再给出入库信息**：

1. **查看 Git 状态**：先查看 git 更改状态（最近提交、暂存区、已修改文件），明确本次待入库的文件与改动内容
2. **编码规范**：确认改动符合项目编码规范（命名、分层、风格、规则文件约定等）；有问题先指出并修正，再往下走
3. **编译确认**：确认相关目标可编译通过；编译失败则先排查修复，不得在未通过时生成「可入库」结论
4. **生成入库信息**：把规范格式的提交说明交给用户，由用户自行 `git add` / `git commit`

## 三、入库信息格式

必须使用下列模板（缺项补全；`ones` 为 bugId，无则填 `0`）：

```text
【项目：XXX】【ones:0】概要描述（处理问题精简关键描述）
【原因：代码层面分析，写明问题出现的原因，不能直接复制测试bug描述】
【改动：如何修改代码逻辑】
【影响面：写清楚受影响的功能模块，使用场景】
【模块：XX】【公共模块：是/否】
```

### 填写要求

- **概要**：一句话说清做了什么 / 解决了什么
- **原因**：从代码/实现层面分析根因，禁止照抄测试或需求原文
- **改动**：说明改了哪段逻辑、怎么改
- **影响面**：写清受影响功能与使用场景；若确实无影响可写「无」
- **模块 / 公共模块**：标明所属模块，以及是否公共模块

### 示例

```text
【项目：kna-pinyin】【ones:0】更改kna-pinyin设置界面ui图标
【原因：kna-pinyin设置界面ui图标大小显示不一致，导致视觉上看着差异化较大】
【改动：更换新的svg图标】
【影响面：无】
【模块：wpspinyin】【公共模块：是】
```
